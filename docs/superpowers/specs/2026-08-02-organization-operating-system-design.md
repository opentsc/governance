# Open TSC 组织操作系统设计

## 目标

把 `opentsc` GitHub Organization 建成 TSC 理论的真实运行实例：中文优先、GitHub 驱动、文档优先、组织即代码、人类与 Agent 共同治理，并允许组织在实践中持续进化。

## 权威边界

- Git 仓库中的创世承诺、法典、事件记录和校准记录构成可移植的“魂”。
- GitHub 是当前协作与执行的“壳”，不是不可替代的唯一平台。
- 中文是权威版本；英文只作为翻译，中英文冲突时以中文为准。
- 联系方式、设备、投入时间等个人资料不得进入公开仓库或 Git 历史。

## 仓库结构

1. `governance`：公开治理中心，承载创世层、双法典、RFC、ADR、制度和 Discussions。
2. `.github`：公开组织主页和默认社区健康文件。
3. `organization-infrastructure`：私有组织即代码仓库，承载期望配置、自动化、审计和运行手册。
4. `tsc`：理论与白皮书（魂的理论来源）。
5. `opentsc`：软件实现（当前壳）。

## 治理模型

- 每个正式治理席位由“一名人类 + 一个配对 Agent”组成。
- 人类议会与 Agent 议会分别审议核心变更。
- 核心变更只有在全体有效人类席位同意、Agent 议会全体有效席位同意、创始人未否决、冷静期结束且审计记录完整时才生效。
- 创始人 `cat9999aaa` 是 Organization Owner、创世层守护者并拥有一票否决权；否决必须留下理由和时间记录。
- 日常可逆操作由预先授权的普通 PR 流程执行，避免所有小改动陷入全体表决。
- 在 Agent 席位尚未建立前，核心文件状态为“启动期草案”；创始人可搭建基础设施，但不得把草案宣称为已获双议会正式批准。

## 协作界面

- Issues：可执行任务、缺陷、提案入口。
- Pull Requests：所有可版本化变更的审阅和生效入口。
- Discussions：公告、一般讨论、问答、想法与 RFC 审议论坛。
- Projects：跨仓库路线图、治理工作和组织演化状态。
- Teams：按治理功能和动态使命分组，不采用前端、后端、测试等传统部门结构。

## 安全与权限

- Owner 极少，创始人保留最高权限。
- 组织默认仓库权限为 `none`，成员通过团队获得最小必要权限。
- 普通成员不能自行创建组织仓库。
- 公开仓库启用可用的安全扫描、依赖安全更新与基础分支保护。
- GitHub Free 不支持组织级 Ruleset，当前使用仓库级分支保护；升级套餐后再统一下沉为组织规则。
- 不在未核验全员 2FA 状态前强制 2FA，避免 GitHub 自动移除成员。

## 持续进化

组织结构不划分永久“阶段”。所有结构都是当前有效版本，通过实际运行、RFC、证据、回顾和校准持续修改。长期未使用的规则、团队、自动化和模板进入日落审查。

## 成功标准

- 三个基础仓库存在且内容完整。
- 论坛、Project 和治理团队可访问。
- 组织权限和仓库保护符合最小权限原则。
- 核心治理变更流程、创始人否决权和人机双议会规则有明确文本。
- 新成员能从组织主页进入论坛、路线图和治理文档。
- 邀请状态、资产状态和安全设置经过 API 复核。
